# TinDog — מסמך אפיון בדיקות

## מטרה

להגדיר מה זה אומר שהמוצר "עובד": התהליכים העסקיים המרכזיים רצים מקצה לקצה, קלטים לא תקינים נחסמים, ומשתמש לא יכול לגשת למידע שאינו שלו.

## שכבות הבדיקה

| שכבה | כלי | מה נבדק | היכן |
|---|---|---|---|
| Unit | Vitest | ולידציות Zod, לוגיקת חפיסה טהורה | `src/lib/__tests__/` |
| Component | Vitest + React Testing Library | קומפוננטות מרכזיות במנותק (עם mock ל-actions) | `src/components/**/__tests__/` |
| E2E | Playwright | התהליך העסקי המלא מול אפליקציה + Supabase אמיתיים | `e2e/` |
| DB / הרשאות | SQL ידני מתועד | מדיניות RLS | סעיף 6 |

## 3. בדיקות לתהליכים עסקיים מרכזיים

התרחיש המלא ממומש כ-E2E סריאלי אחד (`e2e/main-flow.spec.ts`):

1. בעלים נרשם ומפרסם כלב לאימוץ
2. מאמץ נרשם, מסנן, מוצא את הכלב ומחליק ימינה
3. החפיסה מתרוקנת (הכלב לא יוצג שוב)
4. הבעלים רואה את הבקשה עם פרטי המבקש ומאשר
5. הבקשה נעלמת מהממתינות ומופיעה כהתאמה
6. שני הצדדים מתכתבים בצ'אט

## 6. בדיקות RLS ידניות (SQL Editor)

להריץ ב-Supabase SQL Editor עם שני משתמשי בדיקה:

```sql
-- כמשתמש B: ניסיון לעדכן כלב של משתמש A — צריך להחזיר 0 שורות
update dogs set name = 'hacked' where owner_id = '<user_a_id>';

-- כמשתמש B: ניסיון לקרוא הודעות של שיחה של אחרים — צריך להחזיר 0 שורות
select * from messages where request_id = '<request_of_others>';

-- כמשתמש B (לא בעל הכלב): ניסיון לאשר בקשה — צריך להחזיר 0 שורות
update match_requests set status = 'approved' where id = '<request_id>';
```

## 7. בדיקות UI בסיסיות

- כל הטפסים מציגים שגיאות עם `role="alert"` (נגישות + נבדק אוטומטית)
- מצבי ריק (אין כלבים / אין בקשות / אין התאמות) מציגים הסבר והנעה לפעולה — ממומש ונבדק ב-E2E
- כפתורים נחסמים בזמן שליחה (pending) — ממומש בכל הטפסים
- בדיקה ידנית ברוחב מובייל (375px): ניווט, חפיסה וצ'אט שמישים
