# TinDog — מסמך אבטחה בסיסית

## Authentication (הזדהות)

- **Supabase Auth** עם אימייל וסיסמה. הסיסמאות מנוהלות ע"י Supabase (bcrypt), לא נשמרות אצלנו.
- ה-session נשמר ב-**HTTP-only cookies** דרך `@supabase/ssr` — לא נגיש ל-JavaScript, מה שמנטרל גניבת token ב-XSS.
- `src/proxy.ts` (middleware) רץ על כל בקשה: מרענן את ה-session ומוודא תוקף מול שרת Auth באמצעות `getUser()` — ולא רק קריאת cookie (שניתן לזייף).

## Authorization (הרשאות)

שתי שכבות בלתי תלויות:

1. **ניתוב** — ה-middleware מפנה משתמש לא מחובר מכל עמוד שאינו ציבורי ל-`/login`.
2. **Row Level Security** — כל טבלה עם RLS פעיל. גם אם שכבת האפליקציה נפרצת או מכילה באג, הדאטהבייס עצמו אוכף:

| טבלה | קריאה | כתיבה |
|---|---|---|
| profiles | כל מחובר (נדרש להצגת שמות) | רק הבעלים |
| dogs | פעילים לכולם; לא-פעילים רק לבעלים | רק הבעלים |
| dog_photos | לפי הרשאת הכלב | רק בעל הכלב |
| swipes | רק שלי | רק בשמי |
| match_requests | רק המבקש או בעל הכלב | יצירה ע"י המבקש (ולא על כלב שלו); עדכון סטטוס רק ע"י בעל הכלב |
| messages | רק משתתפי בקשה **מאושרת** | רק כמשתתף, רק בשמי, רק בבקשה מאושרת |

## פעולות שמותרות רק למשתמש מחובר

כל האפליקציה מלבד דף הנחיתה ועמודי ההזדהות: החלקה, ניהול כלבים, בקשות, התאמות, צ'אט ופרופיל. נאכף גם בניתוב וגם ב-RLS (`to authenticated`).

## מניעת גישה למידע של משתמש אחר

- כל שאילתה רצה עם ה-JWT של המשתמש הנוכחי — Supabase מציב את `auth.uid()` בכל policy.
- ניסיון לעדכן ישות של אחר (כלב, בקשה) מחזיר 0 שורות — הקוד מזהה ומחזיר שגיאה.
- דף צ'אט של שיחה זרה מחזיר 404 (השאילתה פשוט לא מחזירה שורה).
- ב-Storage: משתמש יכול להעלות/למחוק קבצים רק בתיקייה `<user_id>/` שלו (policy על `storage.objects`), והשרת מוודא שכל path של תמונה שמצורף לטופס אכן מתחיל ב-id של המשתמש.

## ולידציה לקלטים

- **Zod בכל Server Action** — טיפוס, טווח, אורך ו-enum לכל שדה; מזהי UUID נבדקים לפני כל שימוש.
- **SQL Injection** — אין SQL גולמי בקוד האפליקציה; כל הגישה דרך Supabase client עם פרמטרים, וה-RPC functions מקבלות פרמטרים טיפוסיים.
- **XSS** — React מבצע escaping אוטומטי; אין `dangerouslySetInnerHTML`.
- **שכבת גיבוי בדאטהבייס** — CHECK constraints על טווחים, אורכים וערכי enum.

## הגנה על קריאות ל-API

- אין REST endpoints פתוחים — כל הכתיבות הן Server Actions שמקבלות את זהות המשתמש מה-session (cookie), לא מפרמטר שהלקוח שולח.
- Next.js Server Actions כוללים הגנת CSRF מובנית (בדיקת Origin).
- ה-anon key של Supabase חשוף בצד לקוח בכוונה (כך המודל של Supabase עובד) — הוא חסר ערך ללא JWT של משתמש, וכל מה שהוא מאפשר כפוף ל-RLS.

## שמירת סודות

- `.env.local` ב-`.gitignore` — לא נכנס ל-git.
- `.env.example` מתעד אילו משתנים נדרשים בלי ערכים אמיתיים.
- בפרודקשן המשתנים מוגדרים ב-Vercel Environment Variables.
- ה-`service_role` key (עוקף RLS) משמש רק בסקריפט seed מקומי ולעולם לא בקוד האפליקציה.

## סיכונים קיימים ושיפורים עתידיים

1. **אין rate limiting** — משתמש זדוני יכול להציף החלקות/הודעות. שיפור: Upstash Ratelimit או Vercel WAF.
2. **אין אימות תוכן תמונות** — נבדק MIME וגודל בלבד. שיפור: סריקת תוכן/moderation.
3. **תמונות בבאקט public** — מי שמנחש URL יכול לצפות בתמונה. שיפור: signed URLs.
4. **אין אימות אימייל בפרודקשן דמו** (מכובה לנוחות הבדיקה). שיפור: הפעלת confirm email + rate limit הרשמות.
5. **אין דיווח/חסימת משתמשים** — נדרש למוצר אמיתי עם צ'אט.
